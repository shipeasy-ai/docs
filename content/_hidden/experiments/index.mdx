Shipeasy **Experiments** lets you ask _"is the new thing actually better?"_ and get a defensible answer.

You define what you want to measure (a **metric**), set up variant payloads (the **groups**), let users land in one bucket or another, log conversions, and look at the dashboard the next morning. The platform handles assignment, exposure stitching, deduplication, daily aggregation, and the statistics.

## The 5-minute mental model

You ship feature X behind a flag. You believe it&apos;ll lift `purchase_conversion`. So instead of just putting it behind a feature flag, you make it an **experiment**: half the eligible users see X, half don&apos;t. Both groups are tracked. The next day, you look at the dashboard and read either _"X lifts conversion by 3.1% (p=0.002)"_ — or _"no significant difference, scrap it."_

The honest version requires more care than that summary, and the docs walk through it.

## When to use a feature flag vs. when to experiment

| Situation                                           | Feature flag | Experiment |
| --------------------------------------------------- | ------------ | ---------- |
| Is the change reversible?                           | ✓            | ✓          |
| Does it have a known clear win (security fix, bug)? | ✓            | –          |
| Do you need an answer to "did it work"?             | –            | ✓          |
| Cheap to ship, expensive to undo (data migration)?  | ✓            | –          |
| Affects a metric you&apos;re paid to move?          | –            | ✓          |

A practical workflow is to use a feature flag first (so the rollout is safe), then **promote the feature flag to an experiment** once the feature is stable.

## Wire the SDK

<InstallTabs npm="npm install @shipeasy/sdk" />

```ts
import { configure, Client } from "@shipeasy/sdk/server";

configure({
  apiKey: process.env.SHIPEASY_SERVER_KEY ?? "",
  attributes: (u) => ({ user_id: u.id, plan: u.plan, country: u.country }),
});

const flags = new Client(currentUser);

// Ask the UNIVERSE, not the experiment — the user lands in at most one of its experiments
const cta = flags.universe("checkout").assign();

// Read a param: the variant's override ?? the universe's default ?? your fallback
const label = cta.get("label", "Pay");
```

```ts
// Wherever the purchase succeeds — the unit comes from the bound user:
flags.track("purchase", { value: orderTotal });
```

`assign()` is side-effect free. The first `get()` read of an **enrolled** assignment logs the **exposure** event; later reads don't re-log — exposures are deduplicated per unit, experiment and group.

## API · `Client#universe(name).assign()`

The user is bound on the `Client` (`new Client(user)`), so `assign()` takes no argument. You name the **universe** — never an experiment — because a universe is a mutual-exclusion pool: the user lands in at most one of its experiments.

`assign()` returns an `Assignment`, which never throws — an unenrolled user still resolves every param:

```ts
interface Assignment {
  name: string | null; // the experiment the user landed in, or null when not enrolled
  group: string | null; // the assigned variant, or null when not enrolled
  enrolled: boolean; // === (group !== null)

  // variant override ?? universe default ?? fallback. First enrolled read logs the exposure.
  get<T>(field: string, fallback?: T): T | undefined;
}
```

Reading `name` / `group` / `enrolled` never logs an exposure — only `get()` does.

<Callout type="info" title="Params are declared on the universe">
  The universe owns the param schema — an ordered list of <code>{"{ name, type, default }"}</code>.
  An experiment's variants may only <b>override the value</b> of a param the universe already
  declares; they can't add fields. That's why <code>get(field, fallback)</code> is always safe: when
  the user isn't enrolled there's no variant, so the value falls back to the universe's default, and
  only then to your fallback.
</Callout>

## What the daily analysis does

<Steps>
  <Step title="Cron enqueues a job per project">
    A scheduled trigger on the Shipeasy fans out one queue message per project that has running
    experiments.
  </Step>
  <Step title="Consumer scans events store">
    For each project, the consumer pulls yesterday&apos;s exposures and events from Analytics
    Engine, joins by <code>user_id</code>, and aggregates per metric × group.
  </Step>
  <Step title="statistical analysis">
    Lift, two-sided p-value, 95% CI. Per metric, per group, vs. the control group.
  </Step>
  <Step title="Persist results">
    Results are persisted to your project, scoped to the project. The dashboard reads them; you can
    export them.
  </Step>
</Steps>

<Callout type="warn" title="Don't peek and stop early">
  The p-values are valid for **fixed-horizon** tests. If you sneak a look every hour and stop the
  moment something turns significant, you'll get false wins. Pre-decide the experiment&apos;s
  duration based on traffic.
</Callout>

<Callout type="warn" title="Don't change variants mid-flight">
  Changing `params` on a running experiment invalidates the analysis. Stop the experiment, create a
  new one with `v2` in the name.
</Callout>
