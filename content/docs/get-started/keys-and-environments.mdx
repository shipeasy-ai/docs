Shipeasy has exactly two kinds of SDK key. One per entrypoint, one configure call per side. Get this right and everything else — env isolation, public-bundle safety, evaluation scope — falls out for free.

## One key per entrypoint

|            | **Server key**                               | **Client key**                         |
| ---------- | -------------------------------------------- | -------------------------------------- |
| Import     | `@shipeasy/sdk/server`                       | `@shipeasy/sdk/client`                 |
| Field      | `apiKey`                                     | `clientKey`                            |
| Visibility | **Secret** — never ships to a browser        | **Public** — ships in your bundle      |
| Reads      | Full rule set (gates, configs, killswitches) | Only client-readable flags and configs |
| Writes     | Events                                       | Events, rate-limited by domain         |
| Env        | Bound env is the default; `?env=` overrides  | **Locked** to its env                  |

```ts
// Server (root layout / startup) — server key ONLY, passed as apiKey
import { configure } from "@shipeasy/sdk/server";
configure({ apiKey: process.env.SHIPEASY_SERVER_KEY ?? "" });

// Client (one "use client" component at startup) — public client key ONLY
import { configure } from "@shipeasy/sdk/client";
configure({ clientKey: process.env.NEXT_PUBLIC_SHIPEASY_CLIENT_KEY ?? "" });
```

<Callout type="danger" title="Never interchange them">
  Never pass `clientKey` to the server entrypoint or the server key to the client. The server key
  authenticates the **full** payload and must never leave your server. A leaked server key in a
  browser bundle exposes every rule you have.
</Callout>

## Where each key goes

<Steps>
  <Step title="Server key → secrets">
    Store it as a deploy secret: `SHIPEASY_SERVER_KEY` in your platform's env, a Cloudflare secret,
    a Vercel encrypted env var. Read it with `process.env.SHIPEASY_SERVER_KEY`. It never appears in
    client code or the network tab.
  </Step>
  <Step title="Client key → public env">
    Prefix it so your bundler inlines it: `NEXT_PUBLIC_SHIPEASY_CLIENT_KEY` (Next.js) or
    `VITE_SHIPEASY_CLIENT_KEY` (Vite). It is meant to be public — the client key only exposes the
    flags and configs you mark client-readable, and the Worker rate-limits it by domain.
  </Step>
  <Step title="Mint and manage">
    Create, rotate, and revoke keys in **SDK keys** in the sidebar, or with `shipeasy sdk keys`.
    Each key is bound to its environment **at mint time** — you pick the env when you create the
    key, not when you use it.
  </Step>
</Steps>

## The read environment is derived from the key

This is the part people expect to be a config flag and it isn't. The environment a key reads is baked into the key when you mint it, and that bound env is what every request reads unless a server key explicitly overrides it (below).

- A key minted for `prod` reads `prod` flags and configs.
- A key minted for `staging` reads `staging`.

So you deploy the prod key to prod and the staging key to staging — there is nothing to set in code. A client key can never be pointed at another env; a server key reads another env only when a request explicitly asks for it with `?env=`.

<Callout type="info" title="Why not a query param?">
  Deriving env from the key means the wrong env is never read **by accident**: with no override, a
  staging key reads staging. A public client key can't be coaxed into reading another environment
  from the browser at all, because it ignores `?env=`.
</Callout>

### Client keys are locked; server keys can override

|                | Per-request env override                                                                                                               |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **Client key** | No. `?env=` is ignored — a `staging` client key can only ever read `staging`.                                                          |
| **Server key** | Yes. A valid `?env=dev\|staging\|prod` on a read wins over the bound env **for that request only**; without it, the bound env applies. |

How the two rules fit together: the env bound at mint time is the **default**, and the per-request override is the **only** way a server key reads anything else.

- The override applies to reads only (`/sdk/flags`, `/sdk/bootstrap`, `/sdk/evaluate`). Events a server key sends are always recorded against its bound env.
- An unknown value (`?env=bogus`) is ignored and the bound env is read — never silently prod.
- It exists so you can preview another env from your machine (for example a dev box reading staging) without minting a key.

A client key is public, so allowing it to switch environments would let anyone with your bundle read any env. A server key is a trusted secret on your own infrastructure, so the per-request override is safe there — but you should still deploy the right key per environment and treat the override as a debugging convenience, not a deploy strategy.

## Env scoping

Each environment is an isolated slice of your project's rules. A flag at 100% in `staging` can be at 0% in `prod`. Use a **separate key per environment** and let the key carry the scope:

<TypeTable
  type={{
    dev: {
      type: "env",
      description: <>Local development. Often the loosest rollouts — flip things on to see them.</>,
    },
    staging: {
      type: "env",
      description: (
        <>Pre-production. Mirror the prod rule shape; ramp ahead of prod to soak changes.</>
      ),
    },
    prod: {
      type: "env",
      description: <>Production. The env your real users read; ramp deliberately here.</>,
    },
  }}
/>

<Callout type="warn" title="One client key per environment — don't share">
  Never reuse a single client key across environments expecting isolation. The key *is* the env
  boundary; sharing one collapses the boundary. Mint `staging` and `prod` client keys separately and
  ship each to its own build.
</Callout>

## SDK key environment variables

<TypeTable
  type={{
    SHIPEASY_SERVER_KEY: {
      type: "string",
      description: (
        <>Server-side key. Read by the server build. Treat as a secret; never expose it.</>
      ),
    },
    NEXT_PUBLIC_SHIPEASY_CLIENT_KEY: {
      type: "string",
      description: (
        <>
          Client-side key. Safe to expose. Vite: <code>VITE_SHIPEASY_CLIENT_KEY</code>.
        </>
      ),
    },
  }}
/>

Anything passed explicitly to `configure({ ... })` wins over the environment variable.
