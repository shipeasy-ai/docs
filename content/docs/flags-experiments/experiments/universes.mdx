A **universe** is the world an experiment lives in. Every experiment belongs to exactly one universe, and the universe owns the three most important guarantees the platform offers:

- **Mutual exclusion** — at most one experiment in the universe assigns each user, so two experiments touching the same surface can never confound each other. This isn't a flag you turn on; it's what a universe _is_, which is why the SDK asks a universe (`universe(name).assign()`) rather than an experiment.
- The **param schema** — the single source of truth for every param in the universe, and the source of the value an unenrolled user reads. Experiments may only override values per variant, never add fields.
- A **holdout** — a fixed bucket range excluded from every experiment in the universe. This becomes a clean global control you can compare aggregate behaviour against.

Most projects start with a single `default` universe and never need another. You add universes when experiments start interfering with each other, or when you want a long-term holdout to measure the cumulative effect of all the experimentation you're doing.

## The mental model

Think of a universe as a population: every eligible user is sliced into one of three buckets the moment they enter.

Bucketing is deterministic: the same `user_id` always lands in the same bucket for the same universe, even across processes and across deploys, because the bucket is `hash("<universe>:<unit>") % 10000` — the universe's **name** is the salt, and the name is immutable after create.

## Holdouts

A 5% holdout in the `checkout` universe means: 5% of users are pinned to never see _any_ experiment in that universe. They always get the legacy code path. With a holdout you can:

- **Measure aggregate program lift.** Compare the conversion rate of holdout users vs non-holdout users to estimate the **net effect** of all your checkout experimentation over time. This is the only honest way to answer _"is the experimentation program collectively worth it?"_
- **Trust individual results more.** When an experiment looks strong, the holdout is the sanity check that the broader population is also moving — a real win shows up in aggregate, not just inside the variant.
- **Roll back instantly.** Kill the universe and on the next poll cycle (≤ plan poll interval, typically 30s–5min), every user falls into the holdout's code path.

Holdouts are **persistent**: a user assigned to the holdout stays in it across experiments and across time. The universe name (the salt) is immutable, so the only thing that can move a user in or out is changing the holdout range itself.

```bash
# --holdout takes a basis-point range, lo,hi (0–9999). 0,499 = first
# 5% of bucketed users sit in the holdout.
shipeasy release experiments universes create checkout --holdout-range '[0,499]'
```

You can change the holdout size later, but realise that bumping it up reshuffles bucketing — some users move in, some out — which invalidates the long-term holdout comparison for that period. Avoid changing it during an active experiment.

<Callout type="info" title="Why a holdout, when each experiment already has a control?">
  An experiment's `control` group still uses every other experiment that's running. The holdout is
  the only group that uses **none** of them. It answers a different question: _"is everything we're
  shipping, taken together, doing anything?"_
</Callout>

## Mutual exclusion

A universe guarantees a user is assigned to **at most one running experiment** in it. The bucket they fall into determines which experiment. There is no `--mutex` flag to turn on — the universe model itself is the guarantee, which is why the SDK asks a universe by name and gets back a single `Assignment`.

Two experiments that touch the same surface can _confound_ each other — if `checkout-cta` and `checkout-layout` overlap on the same users, you can't tell which experiment moved the metric. Mutual exclusion makes the universe a fixed-pie model: experiments compete for the same allocation, you can't over-allocate, and the analysis stays clean.

```bash
shipeasy release experiments universes create checkout --holdout-range '[0,499]'
```

### How allocation slots work

The post-holdout traffic is sliced into a single number line `[0, 1)`. Each running experiment claims a contiguous slice equal to its allocation %. A user's hash maps to a single point on the line; whichever slice contains it is the experiment they get.

```
| holdout 5% | exp A 30% | exp B 20% | exp C 10% | unallocated 35% |
0           .05         .35         .55         .65               1.0
```

Stop experiment A and the slice between `.05` and `.35` becomes unallocated on the next poll. Add experiment D with 15% allocation and it gets appended to the right of the last allocated slice. Allocations don't reshuffle when other experiments start or stop, which keeps user assignments stable.

## The param schema — where values come from

The universe owns the config schema: an ordered list of `{ name, type, default }`. It is the single source of truth for a param across **every** experiment in the universe, and it is what makes reading a param always safe.

```bash
shipeasy release experiments universes create checkout \
  --param-schema '[
    {"name":"label","type":"string","default":"Pay"},
    {"name":"show_badge","type":"bool","default":false}
  ]'
```

An experiment's variants carry an **override map** — a subset of those keys. A variant that doesn't set a key inherits the universe default; a key the universe never declared is **rejected** at create time. So the resolution order the SDK applies on every read is:

```
assign().get(field, fallback)
  → the assigned variant's override
  → else the universe's declared default
  → else your in-code fallback
```

That's why an unenrolled user — held out, untargeted, unallocated, or reading before you ever start the experiment — still gets a sensible value: they fall through to the universe default. Types are `bool`, `string`, `int`, `number`.

<Callout type="info" title="Params used to live on the experiment">
  The experiment-level <code>params</code> map (param-name → type) is deprecated and retained only
  for back-compat. New experiments should leave it empty and declare params on the universe.
</Callout>

## Targeting

Eligibility is decided **per experiment**, not per universe: an experiment can carry a `targeting_gate` (a regular [feature flag](/flags-experiments/gates)) so only callers that pass the flag are enrolled.

```bash
shipeasy release experiments create checkout-cta \
  --universe checkout \
  --targeting-gate logged-in-pro
```

Common shapes for that flag:

- _"Logged-in users only"_ — `attr: user_id, op: neq, value: ""`
- _"Pro plan only"_ — `attr: plan, op: eq, value: "pro"`
- _"Specific country"_ — `attr: country, op: in, value: ["US","CA"]`
- _"Internal accounts excluded"_ — `attr: email, op: not_ends_with, value: "@yourcompany.com"`

Users who don't pass are never assigned and never count toward that experiment's analysis — they read the universe defaults like anyone else. To hold users out of **every** experiment in the universe at once, use the universe's holdout range instead.

## When to add a universe

<Callout type="info" title="A useful default">
  Start with one universe per **product surface**: `checkout`, `onboarding`, `pricing`. Inside each,
  run experiments freely. Across them, you're free to overlap because users on the pricing page
  aren't the same population as users at checkout.
</Callout>

A pattern that works well at scale:

| Universe     | Holdout range | Notes                                                                 |
| ------------ | ------------- | --------------------------------------------------------------------- |
| `default`    | `null`        | Catch-all for cheap tests on different surfaces                       |
| `onboarding` | `[0, 499]`    | 5% — high-leverage area; long-term holdout to measure cumulative lift |
| `checkout`   | `[0, 499]`    | 5% — same                                                             |
| `pricing`    | `null`        | No holdout because we don't want users with weird prices for too long |
| `growth`     | `[0, 999]`    | 10% — long-term holdout for marketing surfaces; report quarterly      |

Rules of thumb:

- **One universe per surface** where experiments could plausibly overlap. The cost is a smaller addressable population per experiment; the benefit is interpretable results — and you get it automatically, since mutual exclusion isn't optional.
- **Holdout 5%** (`[0, 499]`) is the sweet spot for most teams: large enough to detect aggregate lift over a quarter, small enough that you're not parking 1-in-10 users on legacy code.
- **Holdout 0%** is fine when the surface is short-lived (a single launch), when traffic is too low to detect aggregate lift, or when keeping any user on legacy code is unacceptable (pricing, billing).

## Reading the holdout

In analysis, the holdout shows up as a synthetic group named `holdout` on every experiment in the universe. You can compare any variant against the holdout (instead of against `control`) for an end-to-end _"did our experimentation help, vs not experimenting at all?"_ readout.

A typical universe-level summary in the dashboard:

```
checkout universe · last 30 days
  holdout (5%)        N=18,402   purchase_rate=4.6%   AOV=$48.10
  non-holdout (95%)   N=349,671  purchase_rate=5.1%   AOV=$49.40

  Aggregate lift vs holdout:
    purchase_rate   +10.9%   p=0.003   CI [+3.8%, +18.0%]
    AOV             +2.7%    p=0.142   CI [-0.9%,  +6.3%]
```

This is the single best argument for keeping a holdout: it's the only way to detect when your experimentation program collectively doesn't move the needle.

  There is no <code>mutex</code> field — mutual exclusion is intrinsic to a universe. There is no

## Switching a user out of the holdout

Don't. The point is stability. Manually moving users in and out of the holdout breaks the comparability of every aggregate measurement, and it isn't exposed in the API on purpose. If a specific user (e.g. an internal account) must bypass it, exclude them upstream with a [feature flag override](/flags-experiments/gates/overrides) on the experiment's targeting flag rather than reaching into the holdout.

<Callout type="warn" title="Don't change the holdout range mid-experiment">
  The universe name is the salt and is immutable, so buckets can't drift on their own — but widening
  or narrowing `holdout_range` moves users across the boundary. Any in-flight experiment will see
  its assignments reshuffle, the t-test will mix two populations, and results become
  uninterpretable. If you must resize it, stop every experiment in the universe first.
</Callout>
